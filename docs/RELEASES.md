# GitHub builds and release artifacts

## First upload to GitHub

From the extracted source directory, create a repository in your GitHub account, then run:

```bash
git init
git add .
git commit -m "MirrorForge V1 source baseline"
git branch -M main
git remote add origin https://github.com/YOUR-ACCOUNT/YOUR-REPOSITORY.git
git push -u origin main
```

Replace the remote URL with your repository URL. Once CI passes, publish a release by pushing the `v1.0.2` tag below. Keep the separate licence private key outside the repository.

## Create a release

1. Push the source to a GitHub repository with Actions enabled.
2. Confirm the public key file `apps/server/config/license-public-key.pem` is committed.
3. Confirm no private key, admin token, signing certificate, provisioning profile, or keystore is committed.
4. Create and push a version tag, for example:

   ```bash
   git tag v1.0.2
   git push origin v1.0.2
   ```

5. The `Build and release all platforms` workflow builds the desktop matrix, Android APK and iOS IPA. After all jobs finish, GitHub Release is created with the artifacts attached.

## Artifacts

- `MirrorForge-1.0.2-win32-x64-setup.exe` and `MirrorForge-1.0.2-win32-arm64-setup.exe` — Windows installers.
- `MirrorForge-1.0.2-win32-x64-portable.exe` and `MirrorForge-1.0.2-win32-arm64-portable.exe` — portable Windows executables.
- `MirrorForge-1.0.2-linux-x64.AppImage` and `.deb` — Linux x64.
- `MirrorForge-1.0.2-linux-arm64.AppImage` and `.deb` — Linux ARM64.
- `MirrorForge-1.0.2-darwin-x64.dmg/.zip` — Intel Mac (macOS 13+).
- `MirrorForge-1.0.2-darwin-arm64.dmg/.zip` — Apple Silicon Mac (macOS 13+).
- `MirrorForge-1.0.2-android-debug-signed.apk` — sideload/test APK.
- `MirrorForge-1.0.2-ios13plus-unsigned.ipa` — modern unsigned IPA, iOS 13+.
- `MirrorForge-1.0.2-ios9plus-arm64-unsigned.ipa` — legacy display-only client for iOS 9+ on 64-bit devices; 32-bit devices need an older toolchain or Safari.

Exact artifact filenames are generated by electron-builder; verify the artifacts in the Release page after the first GitHub workflow run.

## Signing before public distribution

For Windows, add an Authenticode signing step with a protected certificate and timestamp service. For macOS, sign with Developer ID and notarize with Apple. For production Android, provide a protected upload/release keystore and build a signed release APK/AAB. For ordinary iOS distribution, install the Apple certificate and provisioning profile in a temporary CI keychain and export a signed IPA. All signing credentials should be configured as repository/environment secrets, not committed to source.
## Previous build failure

The first V1 package used a Linux-specific desktop-entry configuration that caused electron-builder schema validation to fail in the reported environment. V1.0.1 removes the entire `build.linux` object rather than relying on a nested desktop-entry schema. Linux package types are supplied on the Linux build command line, so Windows and macOS builds do not parse optional Linux desktop metadata.

## V1.0.1 build repair and legacy display client

The `build.linux` configuration object was removed from `package.json` to avoid the `configuration.linux should be a null` schema validation failure that blocked non-Linux targets in the reported builder environment. Linux targets are now supplied directly in the Linux-specific workflow step (`AppImage deb`) and in the Linux build scripts. This deliberately uses electron-builder defaults for optional Linux desktop metadata.

The `ios-legacy` job builds an independent native Objective-C/WKWebView client at a 9.0 deployment target and packages it as an unsigned arm64 IPA. Its display route uses an ES5 renderer (`/legacy-display/<token>`) rather than the modern dashboard code. It is not an iPad 2 / armv7 build.


## V1.0.2 — avoid duplicate Electron Builder publishing

All desktop build invocations explicitly pass `--publish never`. Per-platform
jobs upload artifacts to Actions, then the single `publish` job creates or updates
the GitHub Release using the workflow-provided token. This prevents `GH_TOKEN`
errors during compilation and avoids duplicate publishing paths. The release job
requires the workflow's `contents: write` permission.
